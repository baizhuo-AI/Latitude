# 自定义字段二期：AI 接管字段 + 输入即建

- 日期：2026-06-17
- 状态：设计稿（待评审）
- 依赖：[2026-06-12 自定义字段系统设计](./2026-06-12-custom-fields-and-grouped-view-design.md) 的 Spec 1 已落地（`field_definitions` 表、`todos.custom_fields` 列、`useFieldStore`、字段管理 UI、`NewTaskModal` 适配均已实现）
- 关联：[2026-06-15 AI 秘书改造方案](../../specs/2026-06-15-ai-secretary-design.md)（工具暴露层、三种大脑的约束来自这里）
- 一句话：在已落地的自定义字段底座上加两条更快的管理路径——① **AI 在对话里全权增删改字段、填值**；② **手动建任务时输入一个新值，当场建成选项**。

---

## 0. 背景与现状

字段系统的**底座一期已经做完**：支持单选 / 多选两类自定义字段，字段定义存 `field_definitions` 表，每个字段挂若干 `{id, label, color}` 选项（10 色预设盘 `PRESET_COLORS`），任务的字段值存 `todos.custom_fields`（JSON，单选存选项 id 字符串、多选存 id 数组）。用户可以在字段管理界面（`CustomFieldsManager`）建 / 改 / 删字段，在新建任务弹窗（`NewTaskModal`）给任务选字段值。

但管理字段现在**只有"手动进设置页"一条路**，由此引出两个缺口：

- **缺口一 —— AI 完全碰不到字段。** AI 秘书暴露给大脑的工具集（`chatTools.ts` 里的 `CHAT_TOOLS`，共 26 个）没有任何字段相关工具；`create_todo` / `update_todo` 也不支持 `custom_fields` 参数。AI 既不能建 / 改 / 删字段，也不能给任务填字段值。
- **缺口二 —— 手动建任务时选项是"死"的。** `NewTaskModal` 里单选 / 多选字段只能从已有选项里选，输入一个新值不会自动建，必须先跳去 `CustomFieldsManager` 建好选项再回来选，打断填写流。

本期补这两个缺口。**不新增数据表、不改数据模型**，只在现有底座上加"入口"。

**本期明确不做（YAGNI）：** 不扩展字段类型——AI 和手动都只能建单选 / 多选，日期 / 数字 / 文本类字段不在本期范围（见 §2-R5）。

---

## 1. 方案

### 1.1 两个能力，一个共享底座

两个能力是同一组底层操作（建选项、建字段、改字段、填值）的两个不同入口：

| 能力 | 入口 | 场景 |
|---|---|---|
| 能力一：AI 接管字段 | 对话（AI 工具调用） | 忙时口头指挥："把这任务归到 X 项目""建个客户字段" |
| 能力二：输入即建 | `NewTaskModal` 表单 | 自己填表时不被打断，输入新项目当场建 |

**关键约束：两条入口必须走同一套底层写逻辑**，并都触发跨窗口同步（`syncBus` 的 `emitSync("fields")`）。否则会出现"AI 建的选项手动界面看不到 / 手动建的 AI 不知道"这类两套逻辑漂移的鬼问题。这套共享写逻辑沉到 `useFieldStore` 的 action（`addField` / `updateField` / `removeField`，底层调 `dbInsertField` / `dbUpdateField` / `dbDeleteField`），两个入口都调它，不各写各的。

### 1.2 能力一：AI 接管字段

#### 工具清单

新增 5 个字段工具 + 改造 2 个现有任务工具：

| 工具 | 类型 | 作用 | 破坏性 |
|---|---|---|---|
| `list_fields` | 新增 | 列出所有字段及其选项（字段名、类型、各选项 label/color）。**其他写操作的前提**——AI 先看清现状才能避免重复建 | 只读 |
| `create_field` | 新增 | 新建单选 / 多选字段，可带初始选项 | 无 |
| `update_field` | 新增 | 改字段名；给字段加选项；改选项 label / color | 无 |
| `delete_field_option` | 新增 | 删字段下某个选项 | **有** |
| `delete_field` | 新增 | 删整个字段 | **有** |
| `create_todo` | 改造 | 加 `custom_fields` 参数：建任务时一并填字段值 | 无 |
| `update_todo` | 改造 | 加 `custom_fields` 参数：给已有任务填 / 改字段值 | 无 |

"把任务 X 归到项目 Y"这种**填值**操作，通过 `update_todo(id=X, custom_fields={项目: Y})` 完成，不单设工具。

#### 行为规则（三条硬约束）

1. **AI 只认名字，内部翻译成 id。** AI 嘴里和工具参数里用的都是字段名 / 选项 label（"项目""前端开发"），但 `custom_fields` 底层存的是选项 id。所有工具内部做 label ↔ id 双向翻译。翻译时做**归一化匹配**（去首尾空格、全半角统一），命中多个同名选项时工具不猜，回报"有歧义，请指明是哪个"。
2. **填值遇到不存在的选项 → 按权限顺手建，但先在对话里说一声。** 用户给了 AI"加选项"权限，所以 `update_todo` 填一个还不存在的选项时，AI 可新建该选项再填——但建之前在回复里明示（"项目里没有'X'，我新建了一个"），给用户一个叫停的机会。等价于能力二的"轻确认"，只是发生在对话流里。
3. **破坏性操作先报告影响、确认后才执行。** `delete_field` / `delete_field_option` 会连带清除所有任务里引用它的值（底层 `dbClearFieldFromTodos` / `dbClearOptionFromTodos`，一期已实现）。AI 执行前必须先报告影响范围（"删'项目'字段会清掉 12 个任务的项目归属，确认吗？"），用户确认了才真删。这与一期**手动删字段已有确认弹窗**的策略一致；手动删选项一期是静默的，但 AI 代删因为用户没亲眼盯着选哪个，统一要求确认，更稳。

#### 工具暴露层（关键实现要求，三种大脑都要能用）

按 AI 秘书设计，工具要同时覆盖两条派发路径才能让三种大脑都用上：

- **MCP server（端口 42800）** —— Claude Code / Codex 大脑走这条；
- **app 自派发** —— 纯 API 大脑走这条（`chatTools.ts`）。

**实现待确认点：** 需先确认现有 26 个工具是"单一真相源、两条路径自动生成"，还是"两处分别维护"。若是后者，本期 5+2 个工具要在两处都注册，否则只挂 `chatTools.ts` 会导致 CC / Codex 用户用不了 AI 管字段。这条在写实现计划前要落地确认（见 §3 第 0 步）。

### 1.3 能力二：输入即建（`NewTaskModal`）

- 把单选 / 多选字段的选择器，从"只能选已有"改成"**可搜索、可输入**"。
- 输入一个匹配不到任何现有选项的值 → 下拉列表底部出现"**+ 新建『XXX』**"项 → 回车 / 点击确认 → 当场建该选项（分配一个 `PRESET_COLORS` 颜色）并选中。
- **轻确认**：新建动作要用户主动触发（点"+ 新建"项或回车），不是输入即静默建——挡掉手滑和错别字（用户选了这个兜底策略）。
- **防重**：判断"是否已存在"用和 §1.2 规则 1 同一套归一化匹配（"项目A"输入"项目 A"应命中已有项、提示"已存在"，而不是建重复项）。
- **适用所有单选 / 多选字段**，不只"项目"——交互统一，将来加新字段自动享有，无需单独配置。

### 1.4 跨窗口同步

AI 在对话窗口、用户在主窗口 / 浮窗，分属不同的 store 实例（多窗口 store 隔离）。任何字段写操作（建 / 改 / 删字段、加 / 删选项、填值）完成后，统一广播 `emitSync("fields")`（值改动广播 `emitSync("todos")`）；各窗口 `onSync` 后重新 `hydrate` `useFieldStore` / todo store。这套机制一期已有，本期照搬，确保 AI 改完字段，主窗口下拉立刻能看到。

## 2. 风险点

> 按"会不会真发生 × 发生了多严重"排序，最高在前。

**R1〔实现〕AI 删字段误伤数据** — 最高危
- 触发：用户随口"把那字段删了"，AI 调 `delete_field`，连带清空所有任务里该字段的值，不可逆。
- 影响：用户，数据永久丢失，严重。
- 缓解：删字段 / 删选项强制走"先报告影响范围 → 用户确认 → 才执行"（§1.2 规则 3）；进一步可加软删除兜底（标记隐藏、保留数据、可恢复），作为本期可选项。

**R2〔体验〕同名 / 近名选项让 AI 填错或建重** — 高
- 触发："项目A"与"项目 A"并存，或用户口述与已有选项差一个空格，AI 按 label 找 id 找错 / 找到多个 / 误建重复。
- 影响：AI 静默填错值，用户不易察觉；或选项列表越积越脏。
- 缓解：归一化匹配（§1.2 规则 1）；命中多个时 AI 报歧义不猜；能力一 / 能力二**共用同一套防重逻辑**，不写两份。

**R3〔产品〕AI 全权 + 自动建 → 字段 / 选项膨胀** — 中
- 触发：多轮对话里 AI 反复建字段 / 选项，几周后字段列表一团乱。
- 影响：用户，可用性下降。
- 缓解：AI 任何建操作前先 `list_fields` 查近似项、优先复用；"建字段"门槛高于"加选项"（建字段 AI 应先跟用户确认意图，而非顺手建）。

**R4〔实现〕工具只挂一条路径，CC / Codex 大脑用不了** — 中
- 触发：本期工具只加进 `chatTools.ts`，没同步进 MCP server（端口 42800）。
- 影响：用纯 API 大脑的用户能用 AI 管字段，用 Claude Code / Codex 的用户不能——能力残缺且隐蔽。
- 缓解：§1.2 工具暴露层要求；§3 第 0 步先确认两条路径的注册关系再动工。

**R5〔产品〕字段类型只有单选 / 多选，AI 会被要求建不支持的** — 中
- 触发：用户对 AI 说"建个截止日期字段"，但系统只有单选 / 多选两类。
- 影响：AI 报错或硬塞成单选，体验割裂。
- 缓解：本期划清边界——AI 只能建单选 / 多选，遇到日期 / 数字 / 文本请求**明确回"暂不支持"**，不硬塞。扩展字段类型另立项。

**R6〔实现〕多窗口漏刷** — 低
- 触发：AI 在对话窗改了字段，主窗 / 浮窗下拉仍显示旧选项。
- 影响：用户看到不一致，困惑。
- 缓解：所有写操作后 `emitSync("fields")`，各窗口 `hydrate`（§1.4）。机制现成，照搬即可，风险低。

## 3. 方法（实施路径）

> 颗粒度到"做哪几件事、先后、依赖、怎么验收"，不到函数级。建议能力二先上（改动小、当天见效），能力一随后。

**第 0 步 —— 确认工具暴露层（动工前必做）**
- 做：查清 `chatTools.ts` 的 `CHAT_TOOLS` 与 MCP server（42800）工具列表是同一份真相源还是两处分维护。
- 产出：一句话结论，决定后续工具要注册一处还是两处。
- 依赖：无。

**第 1 步 —— 能力二：输入即建**
- 做：改 `NewTaskModal` 里单选 / 多选字段的选择器为可输入 + "+ 新建" + 轻确认 + 归一化防重；把"建选项"逻辑沉进 `useFieldStore` 的共享 action，写后 `emitSync("fields")`。
- 依赖：无（底座已具备）。
- 验收：新建任务时在项目字段敲一个新名字，确认后该选项进了 `field_definitions`、其他任务也选得到；输入"项目 A"（已有"项目A"）提示已存在而非建重复；主窗 / 浮窗下拉同步刷新。

**第 2 步 —— 能力一：AI 读 + 填 + 建 / 改**
- 做：先加只读 `list_fields`；再加 `create_field` / `update_field`，并给 `create_todo` / `update_todo` 加 `custom_fields` 参数；全部复用第 1 步沉下来的共享 action 和 label↔id 翻译。按第 0 步结论注册到一处或两处。
- 依赖：第 1 步（共享 action）、第 0 步（暴露层结论）。
- 验收：对 AI 说"建个'客户'单选字段，选项 A/B/C"→ 字段管理页出现它；说"把任务 X 归到项目 Y"→ 任务被填上；说"归到一个不存在的项目 Z"→ AI 明示新建了 Z 再填。

**第 3 步 —— 能力一：破坏性操作（带确认）**
- 做：加 `delete_field` / `delete_field_option`，实现"先报告影响范围 → 确认 → 才执行"；接一期已有的 `dbClearFieldFromTodos` / `dbClearOptionFromTodos` 清理。
- 依赖：第 2 步。
- 验收：说"删客户字段"→ AI 先报"会清掉 N 个任务的值"、确认后才删；删完主窗 / 浮窗同步刷新。

**贯穿全程：** 所有写操作后触发跨窗口同步（§1.4）；能力一、能力二共用同一套防重 / 翻译逻辑（§1.2 规则 1）。

## 4. 待定与假设

- **〔假设〕破坏性操作要确认。** 基于用户对手动输入即建选了"轻确认"，推断其对 AI 删字段 / 删选项也希望先确认——故 §1.2 规则 3 默认带确认。**若用户其实想让 AI 删东西也别啰嗦、直接执行**，去掉这层即可（仅影响 `delete_*` 两个工具的交互，不影响其余）。
- **〔待确认〕工具暴露层关系**（§1.2 / §3 第 0 步）：`chatTools.ts` 与 MCP server 是单一真相源还是两处分维护——决定工具注册一处还是两处。动工前确认。
- **〔已替用户拍板〕输入即建适用范围 = 所有单选 / 多选字段**（非只"项目"）。单独给"项目"开小灶是特例、更难维护。如需收窄到仅"项目"再议。
- **〔边界〕本期不扩展字段类型**（§2-R5）。日期 / 数字 / 文本类字段另立项。
- **〔软删除兜底〕** R1 的删字段软删除（保留数据可恢复）是本期**可选增强、非必须**。最小实现 =“确认弹窗 + 硬删 + 清理”（与一期手动删除一致，**不改数据模型**）。若选择做软删除，需给 `field_definitions` / 选项结构加一个隐藏标记位——这是 §0“不改数据模型”的唯一可能例外，做不做留到实现计划阶段定。
