# 维度（原 Daybreak）：现实采集接入的背景与愿景

- 日期：2026-08-10
- 状态：产品背景同步
- 范围：只描述产品愿景、体验闭环和软件/硬件边界；不包含硬件选型与实施方案

## 1. 背景

Daybreak 已经具备待办、目标、日历、活动记录、每日纪要、长期记忆、主动秘书、MCP
和飞书入口等能力。它已经能帮助用户整理被明确输入的信息，但当前上下文主要来自：

- 用户想起来后手工填写；
- 用户主动与 AI 对话；
- 日历、飞书等已有软件系统。

这意味着软件知道的是“用户记得告诉它的事情”，而现实生活中大量有价值的线索仍然会丢失：
临时承诺、讨论中的决定、突然出现的想法、人与项目的变化，以及一天实际怎样度过。

独立的 AI Listener 项目正在探索一个低摩擦现实采集入口。产品层已经形成一个关键判断：

> **被动采集和主动交互应当分离。**

随身设备只安静、可靠地记录；用户回到桌边后，通过交互充电底座和维度软件完成同步、
理解、确认和后续行动。完整 AI 不需要塞进随身设备，原始录音也不应未经筛选直接变成任务和记忆。

## 2. 产品愿景

“维度”不是一个录音转写工具，也不只是一个更聪明的待办应用。它希望成为一个本地优先的
个人现实上下文系统：帮助用户看清工作、关系、健康、兴趣等不同维度如何占据自己的时间、
注意力和承诺，并在恰当的时候把现实转化为行动。

理想闭环是：

```text
现实发生
  → 低摩擦采集
  → 形成带证据的候选理解
  → 用户快速确认或纠正
  → 写入活动、任务、记忆和每日纪要
  → 主动秘书在以后恰当地帮助行动与复盘
```

重心不是“尽可能多地记录”，而是“用尽可能少的打扰，留下真正重要且经过认可的上下文”。

## 3. 目标体验

一个典型日常体验：

1. 用户白天携带录音胶囊；设备不要求联网，也不承担完整语音助手交互。
2. 用户回到桌边，把胶囊放入交互充电底座。
3. 录音自动同步到维度，软件完成完整性校验、转写和信息整理。
4. 底座或桌面端只提出少量高价值问题，例如：
   - “你答应周五前发方案，要建待办吗？”
   - “这段讨论是否属于项目 A？”
   - “你提到不想安排晨会，要记住这个偏好吗？”
5. 用户确认、修改、稍后处理或拒绝。
6. 只有确认后的信息进入 Todos、Activity Log、Memory Facts 和 Daily Digest。
7. 维度以后可以据此续接昨天、提醒承诺、理解负荷并帮助复盘。

用户最终看到的应是少量可靠结论，而不是一天的录音文件和冗长 transcript。

## 4. 信任原则

### 4.1 证据先于结论

每条由录音产生的候选信息，都应能回到对应原文和音频时间段。模型的理解不是事实本身。

### 4.2 候选先于写入

录音、转写和模型抽取属于“观察层”；Todo、Memory、Activity 属于“确认后的真相层”。
默认情况下，两层之间必须经过用户确认。

### 4.3 本地优先

桌面端本地数据库继续是唯一真相源。原始录音默认保存在用户设备；如调用云端 ASR 或模型，
软件需要明确披露供应商和上传范围，并提供保留、导出和彻底删除能力。

### 4.4 可纠正、可撤销

用户可以修改或拒绝候选，也能看到一条记忆或任务来自哪里。系统不能把不确定推断悄悄固化为
“关于用户的事实”。

### 4.5 大脑可替换

证据语义、确认流程、权限与最终写入属于维度，不属于某个 ASR 或大模型。更换模型不能改变
数据安全边界。

## 5. 项目责任边界

### 5.1 AI Listener 项目负责硬件采集层

目录：`~/Documents/AI listener`

负责：

- 录音胶囊硬件、固件、麦克风和本地存储；
- 功耗、续航、重量、佩戴和声学测试；
- 交互充电底座的硬件、固件、电气和结构；
- 设备侧录音文件、时间戳、manifest、校验和传输；
- 断电、存储满、传输中断和安全回收等可靠性；
- 向维度交付稳定、版本化的设备数据接口。

硬件选型、nRF52840、微雪 ESP32-S3 AMOLED、磁吸触点、充电电路和外壳方案均留在
AI Listener 项目维护，不进入 Daybreak 软件重构文档。

### 5.2 Daybreak／维度项目负责软件理解层

目录：`~/Documents/Daybreak`

负责：

- 识别设备和接收录音的桌面端入口；
- 导入队列、断点恢复、幂等和完整性校验；
- 音频规范化、VAD、ASR 和 transcript；
- 从 transcript 生成带证据的候选理解；
- 与现有 Todo、Calendar、Activity、Memory 去重和对账；
- 桌面端及底座所需的确认状态和交互接口；
- 用户确认后的事务写入；
- 让 Daily Digest 和主动秘书只使用符合权限策略的上下文；
- 通过 MCP 向外部 Agent 暴露受控能力。

### 5.3 双方唯一需要共同维护的边界

硬件与软件通过一个小而稳定的版本化协议对接。软件层至少需要从硬件获得：

```text
protocol_version
device_id
recording_id
started_at
duration_ms
byte_length
content_checksum
recording_state
audio_file
```

软件只有在文件完整接收、校验并持久化之后，才向设备返回可回收确认。具体电气接口、传输介质
和底座结构属于硬件项目；录音进入电脑后的处理状态、候选确认和业务写入属于维度项目。

## 6. 对维度软件方向的影响

现实采集应被视为一个新的输入渠道，而不是一个独立“录音功能页”。软件层需要逐步具备三种
语义层次：

1. **Evidence**：录音与 transcript，回答“原来发生了什么”；
2. **Observation**：模型从证据中提取的机器观察，仍可能错误；
3. **Proposal**：建议对任务、活动、记忆或纪要做出的变化，等待确认。

现有 Todos、Activity Log、Memory Facts 和 Daily Digest 继续作为确认后的落点，不另建一套平行
业务系统。主动秘书默认只根据已确认内容采取行动；未确认内容最多以疑问形式向用户求证。

在界面上，更合适的产品入口是“待确认的现实线索”或“收件箱”，而不是让用户管理大量录音。

## 7. 当前共同决策

- 产品对外名称使用“维度”；代码仓库、数据库和 MCP 等内部标识暂时保留 Daybreak，品牌迁移另做。
- AI Listener 和 Daybreak 继续保持两个项目，各自负责硬件层与软件层。
- 随身端强调低功耗可靠采集，完整推理留给桌面软件。
- 桌面 SQLite 是长期数据的唯一真相源，底座不维护另一份长期记忆。
- 默认确认后才写入任务和记忆，不以“全自动”作为首版目标。
- 软件闭环可以先用现有录音样本开发，不依赖定制硬件完成后才开始。

## 8. 成功标准

这次协作成功，不是因为维度“支持导入录音”，而是因为它能够：

- 可靠接住硬件采集的数据，失败可恢复且不会重复；
- 把长录音压缩为少量值得处理的候选；
- 让每个候选可追溯、可纠正、可拒绝；
- 只把用户认可的内容变成任务、记忆和活动；
- 在之后的简报、提醒和复盘中，真正用这些上下文减少用户的认知负担。

AI Listener 负责让现实可靠地进入系统；维度负责让这些现实变得可理解、可信任、可行动。
