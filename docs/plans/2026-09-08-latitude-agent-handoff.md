# 维度 Agent：知识治理与双链 Runtime 交接

更新时间：2026-09-08。本文用于接续本轮设计讨论；已交付方案与 repo 内 skill 草案，未实施双 Agent 运行链路、未启用治理定时任务。本文的最新用户决策优先于早期文档中的实现建议。接手时先验证当前工作区，其他窗口可能已继续开发。

## 1. 任务背景、问题与目标

起点是维度猜用户 MBTI 不准确。讨论关注的不是四个字母本身，而是：原始记录是否到达模型、是否补全背景、是否把职业要求误当人格、是否找到反证、未知是否真实约束结论，以及知识怎样形成、更新和被提取。这些是待验证的问题，不能仅凭聊天把根因判为模型知识不足或思考太短。

目标是围绕“认知 + 行为”形成持续理解用户的能力：既保留当时的动机、预期、情境约束和选择，也能随结果与纠正修订理解；在线对话按需调用这些认识，后台以适当成本维护它们。

Computer History 的复刻与屏幕事件预处理由另一窗口负责，本任务不接管。来源记录、知识、日程等业务记录、桌面呈现分别处理；记录被捕获不等于已形成知识，更不等于模型本轮已看到。

## 2. 用户已明确的结构

**维度 Agent 是外层整体。里面是主对话 Agent 与治理 Agent 两条直链，中间横向交互。**“维度 Agent 内核”是这套整体的运行实现，基于 DSH 二次开发；不要再把它画成双链下面的单独组件。

```text
┌────────────────── 维度 Agent ──────────────────┐
│ 用户对话 / 用户委托 / 其他定时任务   定时复盘 / 记录达到阈值 │
│               ↓                         ↓      │
│         主对话 Agent                 治理 Agent │
│               ↓                         ↓      │
│       理解诉求与执行任务 ──整理委托──→ 分析与整理   │
│               ↓                         ↓      │
│       沟通与承接用户回应 ←─询问信息需求───┤      │
│               ├────回应与澄清──────────→ ┤      │
│               ↓                         ↓      │
│          答复与任务交付             知识写入与修订 │
└────────────────────────────────────────────────┘
```

图表达归属和交叉，不要求模型固定执行每个分析步骤，也不意味着工具循环只能跑一次。两条链可分别暂停、恢复；维度仍以一个秘书的身份面向用户。

| 角色 | 主要职责与入口 | 交叉方式 |
|---|---|---|
| 主对话 Agent | 用户对话、用户委托、其他定时任务，如简报或安排检查 | 可委托治理分析；承接治理的信息需求，决定怎样与用户沟通 |
| 治理 Agent | 定时复盘、记录达到阈值后的认知行为分析和知识整理 | 提供发现与待补信息；接收用户回应、明确纠正和主链整理委托 |

定时不是治理的专属入口，主链也执行定时任务。两边可以分析，按最终责任分工：主对话 Agent 负责沟通和协助，治理 Agent 负责长期认识的组织、证据和修订。

## 3. 最新开发原则：放权与必要边界

用户原话：“少放硬性护栏和防御性编程，尽量做好放权和边界的平衡，而且可以依照dsh框架进行开发。”

开发先给模型清楚的目标、背景、工具及反馈，允许自主检索、分析、决定写什么、怎样沟通及何时停止。只在真实授权、来源身份、必要状态一致性等地方保留最小约束。不要把所有未知都转换成拦截、审批、固定分支或兜底，不把删掉的提示词微观规则搬成代码限制。

先核对并复用 DSH 的执行循环、会话、工具、压缩、重试与扩展能力，需求确实不满足时再二开。允许修改框架实现，也允许直接用现有能力；不要先预设需要自建完整任务平台。

旧 Runtime 文档中的 WorkStore、新 SQLite、租约、收发件箱和拟议工具都是实现候选，不是用户要求逐项落地的硬清单。WorkStore 的需求实质是保存任务进度与交叉状态、支持恢复和去重；现有框架或存储能可靠承担，就直接扩展。实施前对每个新增模块说明：已有能力缺什么，最小补充是什么。不要先堆防御设施再验证主链路。

项目内对应原则见 [知识 Agent 契约与 Skills](../specs/2026-09-07-knowledge-agent-contracts-and-skills.md)：先提供人可读的整体工作说明，再由模型根据材料作语义判断；精确规则只负责契约与真实状态边界。

## 4. 知识形成与读取的已定方向

| 方面 | 决定 |
|---|---|
| 写入单位 | 按事项比较新旧知识，避免逐条屏幕事件建节点；不变是合法常见结果 |
| 背景与分析 | 关注自述动机、认知表征与预期、选择和约束、归因与变化；按需要读取心理学方法，不机械填全模块 |
| 内容形态 | 带背景的简短描述与节点/关系配合，不能只留纯摘要或人格标签 |
| 准入 | 关于用户、有增量、有后续用途、范围与来源可交代；单次情境价值不必等稳定特征才能保留 |
| 证据 | 用户原话、AI 建议、第三方材料分开；同源派生不重复计支持；补背景不能编背景 |
| 修订 | 明确纠正、反例和认识变化优先；未知不被“自信语气”掩盖 |
| 读取 | 短导航 + 按需查询和回源；缺口驱动改查询方向、调整范围、查关联或反证，而非不停翻页 |
| 三类受众 | 代码契约精确；给模型的工作说明简短；长方法与验收细节放设计稿和按需 skills |
| 成本 | 到期/阈值触发，按事项聚合；模型判断深度，观察真实读取量及效果后调优 |

旅游是讨论用的假设例子，不是用户实际计划。若材料明确表达“想缓解疲劳但担心影响交付”，可保留本次恢复目标、预期收益、交付约束及预期代价之间的关系，不直接归为稳定逃避人格。具体图谱类型需要对照现有 schema；不为凑结构误用表示矛盾的关系去表示资源权衡。

## 5. 横向交互和任务进度

主→治理交付问题、材料引用、已有候选和预期结果。治理→主交付发现、证据、未知、希望了解的信息及询问价值；主自主决定问法、时机、合并、延后或不开展。治理不直接对用户挂卡，也不让主照读内部分析。

用户回应先保留原话，再把主的理解单独传回治理。忽略、收起、拒绝、部分回答、已经解决要区分；不回应不表示确认。用户在普通聊天里回答也能关联原信息需求。

共享读取、变化事件和明确委托是三种交叉途径。不是每次聊天都启动治理，也不是每次更新知识都启动询问。同一事项两链分别推进，只有当前工作确实依赖对方结果时等待；等待不占常驻模型运行。

有依据的知识可先提交，信息不足的部分待补。分析候选不等于入库，返回真实写入回执。普通可逆治理写入沿用既有授权，不新增逐条审批。来源和业务记录由可信入口保存，治理维护语义知识，兼容旧写入时复用回执避免重复。

工作区已有大量其他任务修改。不要重置、清理或覆盖未识别的改动；Computer History 相关工作继续由其窗口负责。历史 runtime 提取 skill 的脚本要求另一项目的 query.ts 布局，在本仓库不适用；不要把它的失败视为产品故障或伪报通过。

## 8. 接手后怎么推进

1. 先读本文件和两份双链方案，再核对当前源码与已安装 DSH 能力。用现有能力对应设计需求，删减没有必要的额外模块与防御分支。
2. 明确最小实现范围：外层维度 Agent、两角色配置、各自任务入口、共享知识访问，以及横向交互。先证明模型拿到了正确背景和工具，别只验证配置文件存在。
3. 先跑通主链的对话、用户委托和普通定时任务，以及治理链的定时/阈值整理；接通主委托治理的写入回执，再接治理委托主询问、回应回传。
4. 在真实必要场景补齐等待、恢复、重复投递处理。按现有框架扩展，不预先为假设中的分布式部署搭完整基础设施。
5. 用隔离测试材料走完整链路：能写入也能检索用到；能主动询问也能根据否定或补充修订；主链普通定时任务不被治理阈值挡住。

验收先看用户能否读懂和实际链路是否成立，再看真实模型效果、成本和必要错误恢复。失败沿材料→实际上下文→判断→工具→回执找第一处偏差，不先归因模型知识不足或思考长度。具体上线时机、频率和成本默认值尚未定案，当前交接不意味着自动启用。
