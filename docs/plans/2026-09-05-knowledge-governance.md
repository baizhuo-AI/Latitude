## 1. 功能目的与负责范围

**让维度持续知道什么值得记住、已有认识哪里需要改变，并保证后续回答使用这些改变。**

知识形成和知识维护作为一个独立核心服务：前者从材料中获得新事实和新理解，后者维护新旧知识、证据、关系与派生摘要。定时运行、收到新材料、用户纠正、来源变化，都可以触发同一个服务。

知识形成按“发现值得理解的事情 → 主动补查相关背景 → 提出并比较解释 → 保留有依据的认识”运行。背景检索要在形成解释时发生；[认知—行为理解模块](../specs/2026-09-06-cognition-behavior-understanding-modules.md)围绕认知解释、动机目标、决策选择、行为调节、归因理解、反馈与变化组织方法。模型按问题选择方法，关键背景的变化会触发依赖它的认识复查。本人认知变化与系统纠错分别记录。具体流程与对照验收见细化设计第 2 节和第 8 节。

治理对象不仅是人格画像，还包括用户处境、经历、目标、项目、选择及理由、工作方法、偏好、承诺与结果，以及用户保存的外部资料。模型自己产生的阅读清单、周回顾和综合画像也要治理，不能自动升格成新的独立证据。

本模块接收上游已可读的活动/对话材料、维度直接消息和用户纠正。屏幕采集、网页正文获取、事件去重、对话重建由 Computer History 功能负责，本方案不重复实现。

继续使用已有 Domain 数据库和 Change Set。助手人设属于 Agent 配置；知识库中的用户偏好可供助手参考，但两者不能互相冒充事实或授权。

## 2. 先定义什么才是一条可维护的知识

保留现有节点类型，给关键语义统一约定。不是为所有材料强行填满人格表，也不是每条原始事件都建节点。

| 要表达的内容 | 建议沿用/补充 | 例子 |
|---|---|---|
| 这是谁/什么的事 | scope 中明确内容归属、主体与项目/场景；读取时落实 | 用户工作偏好、维度产品要求、外部论文观点、助手人设需要区分 |
| 具体知道什么 | label + statement；可以单独被纠正的判断有独立身份 | “这批重复提醒用于测试通知”与“长期偏好充分准备”分开 |
| 怎么知道 | 正式 EvidenceRef 关联、支持/反证/纠正角色；作者归属和原始片段版本可回查 | 用户原话、第三方转述、AI 提议不能混为一类 |
| 理解到哪一步 | 保留 authority + status，增加一致的判断说明格式 | 直接记录、暂定解释、存在争议、只在某场景适用 |
| 何时、何种条件适用 | 使用已有 scope、valid_from/to；记录复查原因 | 项目期的截止日期与稳定背景事实不能用相同过期规则 |
| 为什么修订 | 明确版本、原版、变化原因、依赖与回执 | 来源纠正导致解释收窄；旧版本可回看，当前回答引用新版 |

模型的解释保留简短依据、必要的替代解释、适用边界以及什么信息会改变判断。事实节点不需要机械列出人格反证；涉及动机或跨场景特质时才需要更充分论证。对已有数字 confidence 不编造统一换算，先保留原始标记，再用可读的支持与限制说明替代无依据的精确数值。

### 内容归属

至少区分个人知识、外部参考资料、演示/测试内容、派生产物。实现可复用当前 scope/profile，并为缺失值建立迁移映射；不需要另建四个知识库。

归属与可信程度是两个维度。例如演示目标即使标 user_stated，仍然不能进入真实用户上下文；一篇可靠论文也不能证明用户本人具有论文描述的特点。

**不能直接把 scope={} 的旧记录全部丢掉。** 旧记录可能包含确有依据的内容，应通过原始来源和变更记录补归属。无法判断的保留为待判定，可供诊断读取，但不能静默当成确定的个人事实。

### 版本与引用

节点与关键关系增加可校验的内容版本，写入必须说明读过哪个版本。语义上仍沿用已有 claim 的新旧版本关系与 Change Set；版本计数用于防止后台写入覆盖用户刚做的修改。

EvidenceRef 关联以正式关系表为准。payload 中的重复 ID 字段应由正式关联派生，或明确只作兼容读法，不能维护两套相互独立的答案。

图关系先统一含义与方向。例如 supports 使用“依据 → 判断”，derived_from 使用“派生内容 → 来源”；关系 family 由同一规则决定，所有写入入口复用。若旧数据存在“原始消息 → observation”的反向 derived_from，需经有审计的迁移校正，不能让依赖传播代码猜方向，也不能悄悄改写历史。

## 3. 治理具体要做哪些判断

| 情况 | 应有动作 | 虚构示例 |
|---|---|---|
| 新的长期背景 | 创建知识并关联依据，必要时连接已有项目/目标 | 用户说明正在组织一次社区活动，需要持续跟踪准备事项 |
| 只是重述旧认识 | 补充有意义的新依据或不变，不再建近义节点 | 再次确认活动准备进度，不必每次新增“重视进度” |
| 同一材料被多次看见 | 保留接触记录，证据支持不重复计数 | 同一论文 URL/hash 重复出现；重复屏幕由上游处理，治理继承共同来源 |
| 两条意思相近 | 判定是否同一主体、场景、时间和命题后再合并 | “测试通知”与“也需要实际提醒”不能只因都提到提醒就压成一句 |
| 一条混了多件事 | 拆成能单独修正的项，原稿作为组合视图 | 一个候选画像内的多项特质假设依据和把握不同 |
| 新材料推翻解释 | 撤回/替代对应解释，记录新的纠正关系 | 反复添加提醒的动机由猜测修正为本次通知测试 |
| 看起来矛盾，实为不同情境 | 收窄适用范围，允许并存 | 工作交付要求结构，与探索方向时保留选项可以同时存在 |
| 用户情况真实变化 | 关闭旧有效时间，形成新状态 | 用户从考虑参加工作坊变成确认报名；不能改写过去曾犹豫的事实 |
| 信息不足以判定 | 保留竞争解释或待补材料，不强行统一 | 只有工作互动时，不替用户定完整人格 |
| 知识可能陈旧 | 标记需复查，优先核实当前使用所需项 | 日期已过的行动需要结果，不能自动写成完成 |
| 来源撤回/更正 | 找到依赖它的认识和摘要，重新评估 | 旧演示 claim 撤回后，周回顾不能继续把它作为当前依据 |

合并不是删掉不同声音，修订也不是用最近一句话覆盖一切。用户原话提供其经历、意图和偏好的依据，但也要分清是在提出想法、接受建议、作出承诺，还是报告已经完成。

外部资源独立治理：同一资源、同一内容版本可以合并引用，保留各次获取和阅读上下文；内容发生变化时建立版本。标题相同不够，同一个 URL 不同版本也不能强并。搜索命中、已阅读、用户采纳分别记录。领域知识不足时，可按具体任务补充可靠参考资料，不能把“库里有很多 AI 论文”当作已经具备丰富人格知识。

## 4. 一次治理如何运行

### 输入选择

接收新增/修订的材料版本、用户明确纠正、已到复查条件的知识，以及受影响的派生产物。按“到达或修订的时间 + 稳定身份”跟踪进度，不能只按事件发生日期跳过迟到历史。

模型选择本轮值得深入的事项，参考当前目标相关性、新意、重要纠正、少见而有区分力的选择、影响范围与不确定性。频次只是一项线索。调度还应避免旧材料永久饥饿；临近上游原文到期的材料可以优先处理，但不能因此编造缺失内容。

### 分析与改变

先看新增材料涉及的旧认识及原始依据，再决定继续读上下文、找反例、形成新项或暂缓。不同问题可以有不同阅读路径和思考长度。

每个实质改变只需要交代：改哪项、改成什么、依据是什么、为什么值得改、哪些相关项受影响。没有新认识就明确“不改变”，不要求每轮必须产出若干知识或人格结论。

例如，假设用户正在测试活动提醒工具，可以产生以下改变：

> 修订对象：反复添加同一活动提醒的动机解释。
>
> 新依据：假设用户说明，这批重复设置用于检查通知能否正常送达。
>
> 新认识：这批重复设置具有测试目的；不能推广为以后每条提醒都只是测试。
>
> 后续依据：假设用户随后补充，活动临近，也确实需要收到提醒；测试与实际使用可以并存。
>
> 实际操作：补正式纠正关联，修订适用范围，检查依赖旧动机解释的候选画像与摘要。

### 提交与完成

关联修改使用一个事务性变更：节点内容、正式证据关联、关系、版本和待重算标记一起提交。相关项太大时可以分批，但未完成的依赖传播必须保持可见状态，普通回答不能误把它当最新结论。

提交前核对所读版本；如果用户或另一轮任务已修改，重新读回再决定，不用最后写入覆盖。对同一工作项使用稳定幂等身份，进程重试不生成新的近义节点。

成功条件是“处理决定与真实写入回执已持久化”，不是模型输出“整理完毕”。没有写入但决定不变，也要有处理记录及理由；资料不足、服务失败或预算暂停保留为未完成，不能推进成已覆盖。

### 可给模型的工作说明

> 你负责维护维度对用户及其事情的长期了解。阅读这次新增或改变的材料，并查看相关旧认识。选择值得长期记住的新事实，发现旧理解需要补充、收窄或推翻的地方；需要时继续回源、找反例和其他解释。区分本人原话、AI 建议、外部观点和模型推测，尊重当时的情境。对有价值的变化使用版本化工具，保留依据与简短理由；没有值得改变的内容可以不写。不要把自己的旧摘要当成新的独立证据，不要为了完成任务增加标签。完成时记录实际处理范围、变更回执及仍需补充的材料。

代码只约束真实状态、来源边界和持久化一致性。什么重要、怎样解释、是否需要进一步探索由模型判断，不通过关键词白名单或固定思维步骤代替。

## 5. 长期运行的节奏与恢复

首版建议是一个核心服务、两种处理节奏：

| 触发 | 工作 | 对用户的表现 |
|---|---|---|
| 每小时增量检查 | 处理新材料和变更；没有新材料且无待处理事项时不调用模型 | 通常无提醒 |
| 每天综合维护 | 围绕近期变化检查重复、矛盾、范围、陈旧理解和摘要依赖；不机械全库重读 | 在“对你的理解”中看到有意义的变化 |
| 用户明确纠正/忘记 | 尽快修订直接目标，并处理受影响项 | 当轮确认实际改变，后续回答立刻遵守 |
| 来源修订/撤回、知识被使用时发现陈旧 | 将受影响项加入队列 | 需要时说明当前依据限制 |
| 启动/唤醒/失败恢复 | 合并错过的周期，从未完成材料恢复 | 能区分已处理、处理中、待补与暂停 |

周期是建议配置，尚未启用。定时器不能规定模型必须只思考几轮，也不能无上限生成任务。沿用统一用量统计与用户预算；预算耗尽时暂停整理并保留待办，不把暂停当成功。

不复用 `daily_curation`，它目前负责外网阅读；新增独立 `knowledge_governance` 任务类型。复用 DurableScheduler、RunJobStore、AuditLedger 的启动、任务记录和恢复能力，但必须补齐新类型在存储、重试、状态接口中的注册。

后台治理的普通完成文本不能直接走当前通用 scheduler outbox 每小时推送。只有重要且值得核对的新判断、需要用户信息的关键缺口、或持续影响服务的失败才形成提示。队列本身在功能入口可查看。

### 处理账本的最小补充

建议在现有 Domain 中增加治理工作项及处理回执结构，运行记录继续复用 RunJobStore：

- 工作项记录对象身份、输入版本、触发原因、到达顺序、状态、所属 run、已读取到的位置与待补原因。状态至少区分 pending、processing、needs_source、retryable_failure、settled；settled 的结果再区分 changed / unchanged / excluded。
- 回执记录此次用过的来源/知识版本、完成的决定、Change Set IDs 和后续受影响项。写入成功但进程中断时，可以根据回执恢复，不再重复执行。
- 同一对象、同一输入版本、同一处理策略版本不重复入队。新增材料和改过的旧材料都可重新评估；不能用“最近成功时间”一个字段替代实际完成范围。
- 语义写入与该工作项完成回执在同一个 Domain 事务中落地；跨文件运行日志允许稍后恢复对齐。
- 自己生成的摘要/写入不当作新的用户经历再次提取。只有其依赖发生变化，或有明确维护理由时才再次处理，防止后台自我触发和反复强化。

claim_revision_queue 继续负责其既有的结果修订流程，治理工作项可以引用它，不更改其为 outcome 服务的语义。

## 6. 治理后的知识怎样进入回答

这一部分与后台写入同等重要。

1. **先确定本次可用来源与内容范围。** 正常个人回答不带入 demo；本次明确不使用某来源时，依赖该来源的派生认识也遵守限制。外部资源可以用于论证一般知识，不能用来证明用户特质。
2. **读取当前版本与必要的历史说明。** 已撤回、被替代、过期或停放的候选不作为当前事实；存在争议的认识可以返回，但必须与争议原因一起提供。历史回放仍可读历史版本。
3. **按问题选相关知识，并保留依据与限制。** 所需关系跨页时继续读，不因第一页只有支持证据就丢掉反证；涉及 EvidenceRef-only 来源时同时读取正式关联，不能只遍历 nodes/edges。
4. **把派生概况做成可重建视图。** 提供当前项目、目标背景、重要偏好、近期变化及未决问题的简洁入口，每项能继续回源。组织主题随内容变化，不固定为一张人格模板。
5. **不把整个周回顾 payload 当作个人概况反复注入。** 历史快照留在回顾，当前概况引用当前知识版本。摘要不能构成与其原文独立的第二份支持证据。

当前 getPersonalContext 不包含 claim，单纯增加 claim 数量不会自动改善初始回答。需要把治理后的读取契约实际接到 getPersonalContext、knowledge_context、compile_context 以及使用同一知识的桌面投影。

摘要和当前概况属于派生视图，注明依赖版本、生成时间及缺口，不成为新的事实真相源。依赖变化后先标需要更新，必要时回读当前节点；不能继续把旧摘要当最新理解。

| `models.rs` 与数据库迁移 | Source、Evidence、Node、Edge、Change Set | 内容版本、统一归属契约、治理工作项/回执；不要把所有自由解释字段硬编码成数据库列 | G1/G2/G6/G8 |
| `db.rs::context` 与 `compile_context` | 分页、图路径、回源能力 | 来源/主体范围过滤、当前/历史状态契约、证据关联与支持/反证读取；按需继续读 | G1/G5 |
| `knowledge_update` / feedback / 新治理变更接口 | 现有事务、回滚、claim 版本语义 | 支持带依据的范围修订、正式证据关联变化、关系/版本联动；expected revision 校验 | G3/G6 |
| 依赖处理 | 既有 derived_from、supersedes、关联表 | 统一关系方向/family 并迁移旧记录；节点/来源改变后标记相关理解、当前摘要、星状态和投影；不无条件覆写整片知识 | G4/G9 |
| `DomainClient` | 当前知识与变更工具 | 让模型能明确选择补证据、收窄、合并、拆分、待补、不变；稳定幂等键与真实回执 | G3/G6/G7 |
| `DurableScheduler` / `RunJobStore` / `AuditLedger` | 持久任务、重试、审计 | 独立治理类型、材料范围进度、工作项领取与恢复、普通完成不推送 | G2/G8 |
| `dshRuntime` | 动态上下文、现有模型和工具体系 | 独立治理工作说明、处理范围与当前知识视图；变更后下一轮可见 | G5/G8 |
| 用户入口/本地可读文件 | 已有知识展示、共创、纠正、回滚能力 | 知识变化与依据视图；文件编辑经同一版本化 Domain 路径提交 | G3/G4/G6 |

不另建一套人格库，不先引入新图数据库。后续如果召回实测表明 LIKE 无法满足跨表达查找，再针对实体/别名、中文检索、语义召回设计索引；索引可重建，不能承载权威与来源判断。

## 8. 与 Computer History 工作的衔接

按其最新 [PRD](../specs/2026-09-05-computer-history-prd.md) 对齐边界，不重新定义采集协议。

需要上游提供或能回查：稳定材料身份、内容版本、原始来源位置、作者归属与可靠程度、材料覆盖、到达/修订/到期/主动删除状态。若上游还没有就标待接入，不能要求当前治理模块自己重建屏幕对话。

其 PRD 提出的原始事件最长 48 小时保留，对治理有两个直接影响：

- 自然到期后，仍允许保留的摘要/知识可以继续存在，但必须说明原文已到期，不能伪装成仍能逐字验证。不能在知识 payload、审计快照或新的材料文件中复制全文绕过期限。
- 用户主动清理时，处理所有依赖被清理内容的知识与派生结果。多来源知识保留其他独立依据并重新评估；不因一个来源自然到期自动删除所有长期认识。

“本次不用电脑历史”需要传到派生知识读取。“忘记这一认识”与“清理原始记录”分别保留其语义；忘记后避免同一批旧材料下一轮又重建回来。用于抑制重复提取的记录不得保留用户要求删除的原文；具体保留范围沿用用户的删除选择。

可读本地记忆文件是查看/编辑入口，Domain 仍是唯一当前知识源。导出携带 node ID 与版本，文件改动解析为待提交变更；有效修改经过同一版本检查、证据归属和审计后生效。并发冲突或格式错误需要可恢复提示，不能让文件和数据库各自形成一份不同真相。文件 UI/监听归属在实现分工中衔接，这里只负责知识一致性。

## 9. 第一轮治理直接处理什么

先对隔离测试快照生成可读的变更预览与模型回放，再进入自动运行。预览用于看清具体行为，不意味着日后每条系统推测都要逐一审批；运行时沿用用户已配置的可撤销自动写入授权。

| 测试对象 | 第一轮应有处理 | 验证方式 |
|---|---|---|
| demo 节点及其派生回顾 | 隔离真实读取，标明混合来源；保留演示内容本身 | 初始真实上下文不再出现 demo 或它们的无标记摘要 |
| scope 为空但有真实来源的节点 | 回源补归属，保留确有依据的认识 | 不能误删或遗漏有依据的项目背景 |
| 动机得到纠正的节点 | 补正式纠正关系，限定新解释的适用范围 | 按节点回源能读到对应说明；相关人物候选得到复查 |
| 复合人物候选 | 逐项检查依据与把握，必要时拆分；保留用户处理状态 | 已搁置的人格候选不作为当前用户事实 |
| 混合来源的周回顾与旧星状态 | 标记历史/混合来源与依赖问题，重建当前视图 | 当前回答不从回顾复活已撤回知识 |
| URL/hash 相同的外网节点 | 复用同一资源版本，保留各次获取上下文 | 不把来源重复当两份独立支持 |
| 既有可用真实消息与上游材料 | 查找尚未沉淀的重要事实与动机，形成或补充知识 | 记录已处理与待补范围，不为增加数量编写画像 |

历史回填从已存在、可读的材料开始。后续导入的第三方总结必须标明实际到达时间和作者，不能伪装成过去已在 Computer History 中读取的证据；总结引用的本人原话与作者解释继续区分。

## 10. 如何验收它有没有把人理解得更准确

同时检验内容判断和工程一致性，不能只看写了多少条或任务是否 completed。

| 检查 | 测试材料/操作 | 应有结果 |
|---|---|---|
| 来源隔离 | 混合 demo、真实消息、AI 建议、外部文章 | 个人结论只使用适当材料，不把 demo 目标冒充现状 |
| 纠正生效 | 重复设置提醒 → 说明通知测试目的 → 补充实际提醒需求 | 正确修订适用范围，正式证据完整；不一概解释成测试或遗忘 |
| 单次与长期 | 工作验收与开放探索的不同场景 | 允许情境差异，不强行选一个人格标签 |
| 证据独立性 | 同一来源重复截图、资源、摘要 | 不提高独立支持数量；真实多次主动选择仍可作为不同事件分析 |
| 少见重要材料 | 重复日常操作夹着一次明确高影响决定 | 不被高频内容淹没；判断重要性的理由可说明 |
| 作者与主体 | 假设用户设置助手为沉稳人设；外部 AI 建议参加工作坊 | 分别保留为助手设计、建议；不记成用户性格或已确认报名 |
| 状态与时效 | parked 候选、superseded 旧认识、已过截止的行动 | 不当当前事实，不凭到期推断完成 |
| 正式回源 | 更新 observation 并新增纠正证据 | statement、正式链接、版本和变更回执一致 |
| 并发与中断 | 后台处理时用户纠正；提交后任务进程中断 | 不覆盖用户新版本，重试不重写相同知识，不漏待处理项 |
| 来源到期/删除 | 原文自然到期、主动清理、多独立来源 | 按各自语义更新依据可用性与依赖，清理内容不在摘要或审计中复活 |
| 无新增与长时间睡眠 | 多次空轮、错过多个周期、迟到历史导入 | 空轮不机械写入，恢复合并处理；迟到材料可入队 |
| 下一轮真实回答 | 治理后新开维度会话提同类问题 | 实际使用新版理解与依据；过程有可复核读取记录 |

质量记录以“这条认识是否有用、归因是否合理、适用边界是否准确、纠正后是否持续生效、是否漏掉关键材料”为单位；保留用户纠正、原文和反例，不只让同一个模型给自己打分。

把上述虚构场景做成回归测试；另外使用独立的合成对话或经授权且脱敏的材料验证迁移能力。评估历史推断时限定当时可用材料，不能把后续自述或测试标签泄露给模型再宣称盲推断准确。准确记住已知自述与可靠地形成推断分别评价。

技术验收优先覆盖来源/状态过滤、版本冲突、关联事务、依赖传播、幂等恢复及下一轮实际读取。完成这些后进行真实模型回放和用户界面验证，单元测试通过不能替代用户理解质量。

## 11. 实施顺序与交付边界

1. **统一读取范围与修改契约。** 先解决演示混入、失效状态、证据链接脱节、关系方向和版本冲突，否则新增整理会放大旧问题。
2. **接入完整的增量治理服务。** 工作项、回执、模型分析、恢复与安静运行一起实现；同时完成首轮历史回填，允许材料不足时保持待补。
3. **完成综合维护与依赖更新。** 合并/拆分/矛盾/时效处理、派生概况、来源删除传播和本地文件编辑一致性。
4. **完成用户入口与真实回答验收。** 让用户查看现在知道什么、为何改变、如何纠正；验证新的对话实际使用治理结果。

这是工程依赖顺序，不缩减最终核心功能范围，也不把知识质量留作未定义的“后续优化”。每一步都使用覆盖相应失效机制的隔离用例验收。

本文件交付是治理方案；代码实现、数据变更、模型治理回放、定时启用均未执行。
